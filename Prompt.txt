# INTERWEAVE — CANTON ↔ EVM INSTITUTIONAL INTEROPERABILITY PLATFORM

You are the principal engineering team responsible for designing and implementing **InterWeave**, a production-grade developer infrastructure platform connecting Ethereum/EVM assets and liquidity with Canton Network privacy-preserving institutional workflows.

You are not building a simple crypto bridge.

You are building a modular interoperability control plane that allows developers to:

1. Discover and register assets across Canton and EVM networks.
2. Represent the same logical asset across different ledger technologies.
3. Map application identities to Canton Parties and EVM addresses.
4. Query balances and asset state through one network-neutral API.
5. Perform network-local transfers.
6. Lock an asset on one network and create/release an authorized representation on another.
7. Burn a representation and release the corresponding source asset.
8. Generate cryptographically signed attestations about finalized network state.
9. Perform threshold verification of attestations.
10. Coordinate settlement between Canton and EVM assets.
11. Trigger Canton workflows from verified Ethereum events.
12. Trigger Ethereum actions from authorized Canton workflow events.
13. Reconcile canonical asset supply and backing continuously.
14. Provide TypeScript, Python, REST, webhook and CLI interfaces.
15. Provide complete operational visibility, auditability and failure recovery.

## CRITICAL DESIGN PRINCIPLE

Canton and Ethereum do not share consensus.

Never describe or implement cross-network operations as inherently atomic.

Same-network transactions may provide network-native atomicity.

Cross-network transactions MUST be modeled as durable coordinated state machines with:

* source reservation/lock/burn;
* network-specific finality verification;
* threshold attestation;
* destination execution;
* replay protection;
* timeout behavior;
* compensation where safe;
* explicit uncertain/manual-review states;
* reconciliation.

Never mint or release destination assets solely because the coordinator says that a source transaction occurred.

Independent validators must verify source state.

* signer;

# AGENT WORKING METHOD

When implementing each phase:

1. Read the relevant existing repository code first.
2. Read current primary protocol documentation before relying on assumptions.
3. Write/update an ADR for meaningful architectural decisions.
4. Define interfaces and invariants before implementation.
5. Add tests with implementation.
6. Run tests immediately.
7. Never suppress a failing security/invariant test to progress.
8. Keep public APIs network-neutral.
9. Keep network-specific logic inside adapters.
10. Preserve backward compatibility unless an ADR explicitly approves a breaking change.
11. Keep secrets out of source control.
12. Never create placeholder security logic that silently defaults to ALLOW.
13. Never fake finality or attestation in production configuration.
